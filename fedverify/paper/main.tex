\section{Introduction}
% 1. Federated learning removes the need to pool data, and creates three new problems:
%    a curious server, malicious participants, and an unaccountable coordinator.
% 2. Existing work addresses these SEPARATELY. Robust aggregation discards a bad update
%    but produces no auditable account of which client was excluded or why.
% 3. Blockchain-FL work anchors artefacts, but almost always on a permissioned ledger,
%    and the participant cannot independently verify its own contribution was counted.
% 4. Contribution:
%    (a) client-level forensic screening that REUSES a deployed layer-level tamper
%        detector one level up (population = K client deltas, not D weights);
%    (b) per-round Merkle commitment of update digests anchored on a public
%        permissionless L1, with client-verifiable inclusion proofs;
%    (c) the accept/reject decision itself committed, making screening auditable;
%    (d) an end-to-end open implementation, evaluated under DP and Byzantine attack
%        on MNIST/Fashion-MNIST and on patient-partitioned MIT-BIH.
% 5. State the negative result up front: we do NOT beat Krum/median on accuracy.

\section{System Design}
\subsection{Round Commitment}
% delta -> canon (float32 LE, C-order) -> digest = SHA-256(header || bytes)
% -> leaf_i = SHA-256(JSON([i, client_id, digest])) -> root, with leaf COUNT anchored
% beside it (duplicate-last trees are ambiguous without it, CVE-2012-2459 shape).
% Note the digest header binds client, round and sample count, so an update cannot be
% replayed as another client or into another round; position is bound into the leaf.

\subsection{FedVerify-Forensics}
