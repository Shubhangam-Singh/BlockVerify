BlockVerify

Register an AI model’s hash and its per-layer Merkle root. Verification pinpoints tampering to the layer: changed weights, a rogue layer, a removed one, or a reordering.

  • SHA-256 plus a layer-manifest Merkle tree
  • TEAL smart-contract registry
  • PDF certificates and an audit trail

FedVerify

Each federated-learning round commits its client updates to one Merkle root on chain. Any client can prove its update was included, and forensics flags poisoned updates.

  • Per-round commitments and lineage
  • Client inclusion proofs
  • Differential privacy and robust aggregation

Federated Learning

Federated learning trains one model across many parties without pooling their data. Each round, every client trains locally and sends back a delta — how much it wants to change the model. The server averages those deltas.
Two things can go wrong, and this page shows how both are handled:
A malicious client sends a poisoned delta to corrupt or backdoor the model. The Accept / Reject Lineage shows which clients the aggregator screened out, round by round.
A dishonest server could quietly drop, reorder, or rewrite a client’s contribution. Each round therefore commits a Merkle root over its client updates to a blockchain. Verify proof lets anyone re-derive that root in their own browser and check it against the ledger — without trusting this server.
Full threat model and guarantees: fedverify/docs/FEDERATED.md

Photo Shield

Prove that a photo is yours and existed at a given time, and make AI edits of it harder. Your photo is hashed in this browser; only fingerprints are sent.

Two layers. Provenance: the photo's SHA-256 and a perceptual hash (pHash) are signed with your key and anchored on Algorand. Anyone can later check a copy against the public ledger, without trusting this server. The pHash still recognises copies that were re-compressed or resized. Cloak (optional, runs on your own computer): a tiny, invisible perturbation that makes Stable-Diffusion-based editors produce damaged edits. It raises the cost of misuse on some open models. It does not stop closed models.
Design and limits: PHOTOSHIELD_DESIGN.md, photoshield/docs/WHAT_IS_PHOTOSHIELD.md

Honest limits

  • The cloak targets one encoder. It gives no protection against closed models (Grok, Gemini, Midjourney), and re-encoding, resizing, denoising or diffusion purification can weaken or remove it.
  • Provenance proves that these fingerprints existed at a time, signed by a key. It does not stop a fake from spreading, and platforms do not check it automatically.
  • A perceptual match is evidence, not proof: similar photos can collide, heavy edits or crops evade it, and an adversary can deliberately evade pHash.
  • First-to-register is not authorship. Register before posting.
  • Losing your key loses the ability to prove control of past registrations. Back it up.
  • Use it on photos you own.

Algorand Concepts

When you register a model, a unique 16-character Model ID is generated (e.g. a3f9b2c1d4e8f7a0). It is automatically copied to your clipboard. You can also find all your Model IDs in the My Models tab. Keep this ID — you need it for verification and version history.
Go to the Verify tab → upload the model file → paste the Model ID → click Verify. If the SHA-256 hash of your file matches what's stored on the blockchain, it's verified as intact. If it doesn't match, the model has been modified since registration.
Every write operation (register, verify, add version) is broadcast to the Algorand Testnet as a signed transaction. The model metadata is embedded in the transaction's immutable note field. Algorand uses Pure Proof-of-Stake (PPoS) — no energy-hungry mining, finalized in seconds with the same cryptographic guarantees. Every transaction gets a permanent TxID verifiable live on Algorand Explorer ↗.
Algorand transactions are cryptographically signed and finalized by a globally distributed validator network. Once confirmed, a transaction cannot be deleted, modified, or reversed. Any attempt to alter a registered hash would produce a different SHA-256 fingerprint — making tampering immediately detectable when you re-verify the model.

Federated Learning

Imagine ten hospitals that each want a better heart-scan AI. Alone, none has enough patients to train a good one — but patient records legally cannot leave the building, so they can't pool their data.

Federated learning solves this: nobody sends data anywhere. Each hospital trains on its own patients and sends back only the adjustment it wants to make to the shared model — just a list of numbers. A server averages everyone's adjustments into one improved model and sends it back. Repeat for a few dozen "rounds" and everyone ends up with a model far better than any of them could have trained alone.
Pick a training run from the dropdown and you'll see four things:

1. Accuracy per Round — is the model still improving while under attack?
2. Accept / Reject Lineage — a grid with one square per participant per round. Green means their update was accepted, red means it was screened out for looking malicious.
3. Round Commitments — the cryptographic fingerprint of each round, saved to the blockchain.
4. Verify proof — a button that checks, in your own browser, that a participant's update really was included — without trusting our server.
Because someone has to run the averaging server, and everyone else just has to trust it. That server could quietly drop a hospital's contribution, secretly reorder things, or later claim a round contained something it didn't. Nobody could prove otherwise.

So at the end of every round we take a fingerprint of every participant's update, combine them into one short code (a Merkle root), and write that code to a public blockchain. Change one number in one update and the code changes completely. Because it's public and permanent, the server can't tell two different stories — and any participant can check for themselves that their work was counted.
That's the second problem federated learning creates. A bad participant can send a deliberately poisoned update to wreck the shared model — or worse, install a hidden backdoor so the model behaves perfectly on normal inputs but fails on anything carrying a secret trigger. Accuracy looks fine, so nobody notices.

FedVerify-Forensics is our defence. Every round it compares each participant against all the others and asks: is this update abnormally large? Does it point the opposite way to everyone else? Does it contain corrupted values? Anything too far out of line is rejected before it reaches the model, and the decision is recorded on-chain.

The clever part is that this reuses BlockVerify's existing tamper-detection code. Finding a suspicious participant among many is the same statistical question as finding a suspicious layer inside one model — just one level up.
Bright green — a malicious participant that was correctly caught. Good.
Red — a malicious participant that slipped through. Bad.
Amber — an honest participant wrongly excluded. This is the cost of the defence.
Dark green — an honest participant accepted. Normal.

Rows belonging to malicious participants are labelled, so a perfect run is bright green on those rows and dark green everywhere else. A sentence underneath the grid states the outcome in plain words.
When you click Verify proof, your browser runs four checks. It recomputes the fingerprint from the raw data (it does not accept our server's version of it), folds the proof upward, and finally reads the committed code directly from the public blockchain.

TRUSTLESS ✓ — all four passed. The update was provably included, and you did not have to trust us to establish that.
SERVER-TRUSTED — the first three passed, but this particular run was recorded on a local test chain, so there is no public ledger for the final check. Still honest, just weaker — and clearly labelled rather than hidden.
VERIFICATION FAILED — something doesn't match. That's the alarm.
Partly, and we're careful about the wording. The raw data never leaves its owner, but the updates that are sent are derived from that data, and researchers have shown you can sometimes reconstruct training examples from them. "We never sent the data" is not on its own a privacy guarantee.

So we optionally add differential privacy — controlled mathematical noise, calibrated so it is provably hard to tell whether any single record was in the training set. The strength is a number called epsilon (ε): lower means more privacy and lower accuracy. You can see that trade-off directly by comparing runs in the dropdown.

One honest limitation: the protection applies per training example. For heart data that's one heartbeat, not one patient — and a patient contributes hundreds of beats. A true per-patient guarantee needs different machinery, and we don't claim to have it.

Yes — they solve related problems at different stages.

Register / Verify covers a finished model: one file, registered once, checked later for tampering. The question is "has this artefact changed since I registered it?"

Federated covers a model while it is still being built by many parties who don't fully trust each other. The question is "whose contributions actually went into this model, and were any of them malicious?"

They share the same foundations — the same hashing, the same Merkle proofs, the same on-chain anchoring, and even the same statistical tamper-detection code.

Troubleshooting

Each username can perform at most 10 write operations (register, verify, add version) per 60 seconds. This prevents the blockchain from being flooded. If you hit the limit, wait a moment and try again — the Register tab shows your remaining quota after each operation.
The backend server may not be running. Make sure you started it with python backend/app.py from the project root. If using the hosted version, the Render free tier may be sleeping — wait 30 seconds and try again after the first request wakes it up.
